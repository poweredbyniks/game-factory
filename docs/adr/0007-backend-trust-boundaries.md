# ADR-0007: A Java backend that runs the client's engine

**Status:** accepted · 2026-10-03 · backend language changed to Java 2026-10-04

## Context

The factory needs leaderboards, server-side reward validation and purchase verification. Linkstone did
reward validation by porting its Dart engine to Java and pinning both with cross-language vectors. A
factory adds mechanics over time; a port per mechanic does not scale. Games must also stay fully
playable offline. The team works in Java, and Linkstone's Spring Boot code is a proven base.

## Decision

1. The backend is a Java service (Java 25, Spring Boot 4.1, PostgreSQL, Liquibase) in `server/`.
2. It never re-implements game rules. `gf server-engine` compiles the TypeScript engine and mechanics
   into one ECMAScript-only script (`gf-engine.js`), which the service runs through GraalJS. Attempt
   verification is the same code the phone ran.
3. Contracts stay single-sourced: zod schemas → JSON Schema → Java records with contract tests; golden
   and forged attempts with expected verdicts are generated by the TypeScript side and replayed by the
   Java tests.
4. Trust boundaries: the client owns play and the player's own soft economy, offline. The server owns
   what other players see (leaderboards) and what money buys (purchases, entitlements). Soft-economy
   anomalies are flagged, not clamped.
5. Finished attempts sync from an outbox. The server picks the shipped bundle by content hash and the
   effective config by remote payload version and experiment variants. Replay compatibility is a
   contract: every shipped bundle goes to the registry before release, and a mechanic change that alters
   any outcome bumps the mechanic version. Unverifiable is never treated as cheating.

## Alternatives

- **Node/TypeScript service** (the first draft of this ADR): one language, but outside the team's
  strength for the part that needs operating, securing and debugging in production.
- **Java port of each mechanic** (Linkstone): rejected, a port and a vector suite per mechanic.
- **Node sidecar for replay only**: kept as the fallback if GraalJS throughput disappoints; one more
  deployable.

## Consequences

- Every new mechanic is server-verifiable on the day it ships; the server-engine test fails if a
  mechanic is missing from the script.
- Two toolchains (npm and Maven) meet at a build artifact, `build/server-engine/`, produced by CI before
  the Java build.
- Replay proves legality, not human play; leaderboards add plausibility flags and rate limits.
