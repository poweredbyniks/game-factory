# J. Automated build and release pipeline

**Status:** build configuration, release readiness checks and the `gf build` command are implemented.
No native build has run yet: each game first needs its EAS project (§4). Store submission and CI are
Phase 5.

## 1. One app shell, many store apps

`engine/app/app.config.ts` reads only data and returns the Expo config for one game:

| Native setting | Source |
|---|---|
| App name, marketing version | `games/ID/game.json` `name`, `version` |
| Bundle id, package, iPad support, export compliance, blocked permissions | `games/ID/release.json` over `deploy/PLATFORM/defaults.json` |
| Icon, adaptive and monochrome icons, splash, favicon | `games/ID/assets/` |
| EAS project | `release.json` `eas.projectId` |
| Build number | EAS remote version source, auto-incremented on production builds |
| Environment (`APP_ENV`) | the EAS build profile; selects endpoints and platform services ([F §3](06-ios-android-architecture.md)) |

Native iOS and Android projects are generated by `expo prebuild` from that config (Continuous Native
Generation). They are never committed, so twelve games do not mean twelve native projects.

## 2. Commands

| Command | What it does |
|---|---|
| `npm run gf -- build <game> --platform ios\|android\|all --profile development\|staging\|production --dry-run` | Deep validation and release readiness; prints the EAS command; builds nothing |
| `npm run gf -- build <game> --platform … --profile … [--local]` | The same, then compiles the app bundle and runs `eas build` with `GAME_ID` and `APP_ENV` |
| `GAME_ID=<game> PROFILE=<profile> npm run build:ios` (`build:android`, `build:all`) | Shortcuts for the above |
| `npm run gf -- create-game … --ios-id com.studio.game --android-id com.studio.game` | New game with its store identity, listing stub and placeholder icons |
| `npm run gf -- assets icons <game>\|--all [--force]` | Placeholder app art drawn from the theme |

## 3. Profiles

| Profile | Distribution | EAS environment | Platform services | Output |
|---|---|---|---|---|
| `development` | internal | development | development stand-ins | iOS simulator build (no Apple account needed), Android APK |
| `staging` | internal (testers' devices) | preview | stand-ins until real adapters exist (warned) | ad hoc iOS build, Android APK |
| `production` | store | production | real adapters only (enforced) | IPA for App Store Connect, AAB for Google Play |

`--local` runs the same profile on this machine (`eas build --local`): Android needs the Android SDK and
JDK 17; iOS needs Xcode, which the current development Mac does not have.

## 4. How the selected game reaches the build worker

EAS uploads the repository without gitignored files (so without `engine/app/src/generated/`) and without
the local shell's environment. Therefore:

1. Every game has its own EAS project, and `GAME_ID=<game>` is a plain-text EAS environment variable of
   that project in all environments.
2. `app.config.ts` refuses to run on EAS without `GAME_ID`; it never falls back to another game.
3. The app's `eas-build-post-install` hook compiles the game on the worker:
   `npm run gf -- compile "$GAME_ID" --app`.

One-time setup per game, from `engine/app` with `GAME_ID=<game>` set: `npx eas-cli init` creates the
project (copy its id into `release.json` `eas.projectId`), then `npx eas-cli env:create` adds `GAME_ID`
as a plain-text variable for every environment (check the flags with `--help` for the installed CLI).

## 5. Signing

- **iOS**: EAS-managed credentials. One distribution certificate per Apple team, one provisioning
  profile per bundle id. An App Store Connect API key is used for submission.
- **Android**: EAS-managed upload keystore per app; Play App Signing holds the app signing key.
- Secrets live in EAS and CI, never in the repository.

## 6. Versions

| Version | Meaning | Where |
|---|---|---|
| Marketing version | What players see, semver per game | `game.json` `version` |
| Build number | Monotonic per store app | EAS remote version source |
| Engine version | `@gf/core` package version | `bundle.build.engineVersion` |
| Content hash | Hash of the compiled bundle; selects the bundle for server-side replay | `bundle.build.contentHash` |
| Mechanic version | Rules version; bumped by any change to outcomes | `CoreMechanic.version`, in every attempt record |

## 7. Release readiness (`gf build`)

| Check | development | staging | production |
|---|---|---|---|
| Game compiles and deep-validates | error | error | error |
| EAS project id present | error | error | error |
| Placeholder store ids (`com.gamefactory.`, `com.example.`) | warning | warning | error |
| A module would use a development stand-in (IAP, ads, consent, analytics, notifications) | warning | warning | error |
| Backend URL for leaderboards; for purchase verification in production | — | error (leaderboards) | error |
| Store listing per locale, without TODO text | — | — | error |
| Same template, mechanic, rules and modules as another game (App Store 4.3, Play repetitive content) | warning | warning | error |
| Placeholder icons, missing `ascAppId`, iPad screenshots needed | warning | warning | warning |

Today both games are blocked for every profile by the missing EAS project, and for production also by
placeholder ids, development stand-ins, the missing backend and TODO listing text.

## 8. Store accounts and policies

- **Google Play**: publish from an **organization** account (requires a D-U-N-S number). Personal
  accounts created after November 2023 must run a closed test with at least 12 testers for 14 days before
  each new app can go to production, which breaks a monthly cadence.
- **Apple Developer Program**: an organization account shows the studio, not a person, as the seller.
- **Spam rules**: App Store guideline 4.3 and Google Play's repetitive-content policy reject reskins from
  one account. Each game must differ in mechanic or rules and in meta, not only in theme; the readiness
  check enforces the minimum.
- **Native policy**: no background modes, no microphone, no foreground services, no storage or overlay
  permissions ([F §5](06-ios-android-architecture.md)).
- **Privacy**: App Privacy labels and Data safety follow the SDKs in use; Expo modules ship their privacy
  manifests; ATT before any IDFA use; UMP consent in the EU and UK.
- **Audience**: stay out of the Families and kids programs unless the ads setup is compliant.
- **Target API level**: Google Play raises the required Android target every year; yearly Expo SDK
  upgrades cover it once for all games.
- **Tablets**: `supportsTablet` is off by default; turning it on requires iPad screenshots in every locale.

## 9. Over-the-air updates (Phase 5)

`expo-updates` with one channel per profile and a fingerprint runtime version per game. JavaScript and
content changes ship over the air to compatible builds. Every bundle is uploaded to the backend's bundle
registry before its update goes live, so the server can replay attempts made with it. Tuning ships through
remote config, not updates.

## 10. CI (GitHub Actions, Phase 5)

| Trigger | Jobs |
|---|---|
| Pull request | install · `npm run check` (typecheck, tests, golden attempt verification, deep validation) · `gf build --dry-run` per game and profile · `gf server-engine` then `./mvnw verify` in `server/` (contract fixtures through GraalJS) · Playwright smoke for changed games |
| Push to main | the above · development builds for changed games |
| Tag `GAME@x.y.z` | `gf build GAME --platform all --profile production` · EAS Submit to TestFlight and the Play internal track · listing upload · bundle registry upload |
| Nightly | full simulator run per game · level bot analysis · report artifacts |

## 11. Store metadata and screenshots

Listing text lives in `games/ID/store/LOCALE.json`, validated against the stricter of the two stores'
limits:

| Field | App Store | Google Play | Schema limit |
|---|---|---|---|
| Title | 30 | 30 | 30 |
| Subtitle / short description | 30 | 80 | 30 / 80 (two fields) |
| Keywords | 100 | n/a | 100 joined |
| Description | 4,000 | 4,000 | 4,000 |
| Promotional text | 170 | n/a | 170 |
| Release notes | 4,000 | 500 | 500 |

Screenshots: Playwright drives the web export into scripted states at store viewports (for example
1320×2868 for 6.9-inch iPhones, 1080×1920 for Android); caption templates add localized text; Maestro
captures on simulators give the final native look (Phase 5).

## 12. Release checklist

- [ ] `gf build GAME --platform all --profile production --dry-run` reports no errors
- [ ] Simulator report has no inflation, grind or blocking flags
- [ ] Playwright smoke passes on the web export; Maestro smoke passes on both platforms
- [ ] Remote-config payload validated and published with a version; bundle uploaded to the registry
- [ ] App Privacy labels and Data safety match the SDKs in this build
- [ ] Consent flow (UMP) and ATT prompt verified on devices
- [ ] Store listing, icon and screenshots for every shipped locale
- [ ] Release notes generated from the changelog

## 13. Remote-config deployment

`config/remote/GAME.json` is validated by the same schemas as the runtime, versioned, and published as a
static HTTPS file per environment (`release.json` `environments.*.remoteConfigUrl`) or as a single
Firebase Remote Config parameter. Clients activate a new payload on the next launch. Rollback publishes
the previous version. Feature flags under `features.*` act as kill switches.

## 14. Shareable web builds (development only)

`tools/src/scripts/build-artifact.ts GAME` produces one self-contained HTML file for internal playtests
and stakeholder reviews. The web build is a development and test target, not a product.
